Adaptive Difficulty Classification Rubric
Computer Programming 1  |  Week 1 pilot scope  |  FOR INSTRUCTOR VALIDATION
1  Purpose and model boundary
Revised from the supplied “LogiCade Difficulty Rubrics” (three-page proposal). This rubric specifies interpretable gameplay measurements and expert-labeled targets for an L2-regularized multinomial logistic regression (MLR) difficulty classifier. The MLR recommends the NEXT difficulty: need_help, standard, or advance. It does NOT generate challenges or calculate numerical student grades. The local LLM generates candidate challenges subject to separate content validation.
Unit of analysis: one learner × next-stage decision; use ONLY performance evidence observed prior to that decision. Save the exact decision timestamp, prior served difficulty, target objective/prerequisite, model version, and candidate-eligibility rules.

3  Safeguards for interpreting features
Speed is supporting evidence only and must not be treated as automatic proof of competence. Mistakes, retries, failure rate, attempts, and first-try success overlap; check redundancy, collinearity, and whether each adds information. Compare like-for-like opportunities, task type and difficulty; missing is distinct from zero. Establish matched-time pilot medians using a training/calibration sample only, not held-out learners.
Use raw features as the preferred baseline and compare performance against the proposed banded/one-hot features. If bands are encoded, include an explicit missing indicator and avoid redundant dummy columns for regression identifiability. Fit any imputation, scaling, or feature encoding using training data only.

The four-level evidence table above is a reviewer decision instrument; the trained MLR target has only THREE classes. “Insufficient evidence” is a workflow state, not the fourth prediction class. The difficulty labels are ordered educationally; compare multinomial MLR to an ordinal model if appropriate.
5  Reviewer workflow and data protection
Two instructors who teach programming fundamentals/Computer Programming 1 should independently label the same pseudonymous pre-decision histories. Supply the upcoming objective, prerequisite, prior answers/error traces and available assistance. Conceal any existing automated picker recommendation and future outcomes. Have reviewers note concrete evidence for each label. Report initial inter-rater agreement (e.g., weighted kappa, alongside confusion table), then adjudicate disagreements.
Preserve reviewer IDs, label versions, disagreement resolution, timestamp, and evidence notes. Avoid using post-decision performance to assign labels. Participant data should be pseudonymous with access limited to the authorized research team.
6  Prediction, selection and validation
Train a three-class L2-regularized MLR using expert-labeled pre-decision rows. Split by learner, not randomly by row. Choose hyperparameters and preprocessing on training/validation learners, then report held-out macro F1, confusion matrix, per-class recall, and probability calibration. Compare against a simple preapproved rule-based selector. With ~100 students, report uncertainty and avoid claims of broad generalization.
For new players or unclear evidence, start at instructor-approved standard/diagnostic difficulty. The adaptive engine—not MLR—enforces prerequisites, availability, non-repetition, model-failure fallback, and no skipping of mandatory Week 1 outcomes. The LLM then creates a challenge within approved specifications; generated tasks must be verified before serving.
7  Illustrative instructor labeling example
A learner who repeatedly predicts that a local variable changes a global variable, despite guided examples, may merit need_help. A learner who traces values correctly after a short prompt may merit standard. A learner who independently handles a new shadowing example may merit advance. This example is retained from the original draft; the instructor must confirm whether variable scope belongs to the actual evaluated Week 1 syllabus before using it in the pilot.
